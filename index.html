Case 01 · Winder line

Teaching a web app to drive a machine

The rewinder came with its own control software from the machine vendor — a Windows application, in Chinese, with no documentation and no register map. It knew how to tell the PLC to lower the inkjet head and run the conveyor. We didn't.

Replacing it meant learning what it said. So I recorded the PLC's shared data block during live production at 100 ms intervals, across roll after roll, and lined the captures up against the vendor application's own routine for adding a roll. Where a value changed at the moment an operator finished a roll, that was an offset worth a guess. Where a single bit flipped true and the print head moved a beat later, that was a strobe.

The map came out confirmed in both directions — from the recordings and from the vendor's own code — and forty rolls out of forty matched. This is the sequence our gateway now writes:

  1. wordroll diameter
  2. wordroll width
  3. byte rangeroll ID, fixed width
  4. control bitstrobe: roll info ready
  5. —send the inkjet payload, wait for its acknowledgement
  6. control bitstrobe: start printing

Offsets and bit positions are specific to this installation, so they stay on the plant network rather than on this page — the shape of the handshake is the part worth showing.

The part I'd want to be asked about

Writing to that PLC moves a print head and a conveyor with people standing next to them. Getting the software right was the smaller half of the problem; releasing it without hurting anyone was the larger one.

So writes ship disabled. The application reads the PLC by default and says so on screen; enabling writes takes an explicit PLC_ALLOW_WRITE=1 in the environment file, and the console prints a warning that the app will now move machinery. Commissioning ran as a written checklist in plain Indonesian, staged so that nothing electrical happened until the boring parts were proven:

Stage A runs with writes still off — roll saved, label printed, inkjet acknowledging, PLC reading green. If even one of those fails, don't go to Stage B. Adding machine control on top of a foundation that isn't settled only makes the fault harder to read.

Stage B needs the vendor software fully closed, the line stopped or stoppable, someone standing at the machine who can hit stop, and an obviously fake test roll. Save one roll. Then stop and compare it against a roll the old system made.

And when something does fail mid-sequence, the roll is not rolled back. The paper is real; it has been wound and weighed. The system keeps the record and raises a warning naming the step that failed, so the conveyor or the inkjet can be handled by hand.

Case 02 · Weighbridge

A truck scale, read by a browser tab

Weighbridge indicators talk over a serial cable in whatever dialect the manufacturer chose, at whatever line settings someone configured years ago. Nobody at the mill knew the settings, and the manual was gone.

Rather than ask an operator to guess baud rates, the reader negotiates. It opens the port at a candidate configuration, listens for two and a half seconds, and accepts that configuration only if at least two valid frames arrive. A framing or break error is read as evidence of the wrong settings rather than as a crash, and it moves on to the next candidate. Three vendor frame formats are parsed, and the stability flag the indicator sends is honoured — the save button stays disabled while the number is still moving:

// three dialects, one reader
ST,GS,+0000230kg     stable   · kilograms, as sent
USGS+0000090        unstable · divide by ten
ST+0000070          stable   · divide by ten

This runs in the browser, over the Web Serial API. It replaced a clipboard.

And then the internet went down

A mill does not stop weighing because an ISP is having an afternoon. So the same application also ships as a Windows desktop build that bundles a PHP runtime and starts two Laravel API servers locally, creating and migrating their SQLite databases on first launch. The operator sees the same screens; the app just points at localhost instead of the cloud, and syncs when the link returns.

Case 03 · Executive dashboard

Four systems that were never meant to be read together

Once the mill had four systems, the directors had four logins, four report formats and a person whose week partly consisted of copying numbers between them. The fix was not a fifth database. It was a gateway.

Every request from the browser goes to our own server, which holds the credentials and talks to the four upstream systems on the reader's behalf. Their authentication schemes have nothing in common — Sanctum tokens, JWT, a plain bearer token, and one service with no login at all — so each connector normalises its own login shape behind a single interface, caches the token in memory, and retries exactly once on a 401. No upstream credential is ever handed to the browser, and query parameters are whitelisted rather than forwarded, so a stray parameter can't be replayed upstream under our service account.

Numbers that were quietly wrong

The interesting work here wasn't plumbing. It was that several figures looked plausible and weren't, and the only way to find them was to know what the mill actually means by each word.

Tare. Deriving tare as gross minus net is arithmetic, and it is wrong here: net has already had moisture and waste deductions applied. On one real ticket that reads 3,389 kg of tare where the truck's actual tare was 2,990 kg. Tare has to come from the tare field.

Mixed cargo. One truck can carry several materials on one ticket. Filter by material without parsing the mix and a 1,680 kg delivery of DLK reports as the ticket's full 2,770 kg.

Booleans that aren't. The older API returns booleans as the strings "1" and "0". In JavaScript Boolean("0") is true, so every transaction read as finished. Numerics arrive as strings too, which turns a sum into concatenation.

Today against yesterday. A shift three hours old compared against a full previous day always reads as a sixty percent collapse. The delta was red every morning and told nobody anything. Now today is compared against yesterday truncated to the same wall-clock hour in plant time.

None of these throw an error. They render as a number in the right font, in the right box, on a screen a director makes decisions from. That is the failure mode worth designing against.

Case 04 · Warehouse

Stock that two people can touch at once

Spare parts move through a request, an order and a receipt, and each of those can be partially fulfilled, cancelled, or filled with something other than what was asked for. Stock counts are the number everyone argues about, so they have to survive two admins clicking approve at the same instant.

Every stock mutation runs inside a transaction with row-level locking on the product and its log, and writes a before and after snapshot on each line. Approvals happen per item, with the header status recomputed from its lines rather than set by hand. When a supplier ships something other than what was ordered, the receipt can map it to an existing product or create one flagged for SKU review, keeping a link back to what it substituted for — so the mismatch surfaces to purchasing instead of quietly becoming a new part number.

Three activity tables store field-level JSON diffs of what changed, by whom. Documents number themselves from a user-editable template such as SPB/{YYYY}/{MM}/{XXX}, resolved at runtime, because the format changes and it shouldn't need me.

How I work

What a remote team would actually get

I write things down for the person who has to run it

The PLC commissioning guide is written for a maintenance technician, not a developer: what is safe to run during production, what needs the line stopped, what a specific error message means and why it isn't a failure. If I can't explain a system to the person operating it, I don't understand it yet. That habit is most of what asynchronous work is.

I default to the safe state

Dangerous capability ships disabled and is armed deliberately. Read-only is the default; the screen says which mode it's in. Rollback is one line in a config file and a restart.

I deploy and operate what I build

Five systems across shared hosting and Vercel: subdomains, DNS, SSL, MySQL provisioning and migrations, connection pooling tuned to the host's idle timeout and per-account limits, and a CommonJS entry point worked around because the host runs LiteSpeed. Nobody hands these to an ops team. When one breaks at 11pm, it's mine.

I test where being wrong is physical

The gateway that writes to the PLC has eleven test suites, because a wrong byte moves a conveyor. The CRUD systems around it lean on transactions, validation and audit trails instead — which is a real gap, not a philosophy, and it's the thing I'd most want to fix with a team that has the habit already.

I work in the gap between the machine and the web

Most web developers stop at the API. Most automation engineers stop at the HMI. Register maps, serial framing, port contention with vendor software, and what happens when the thing on the other end of the cable was documented in 2011 in another language — that's the part I've turned out to like.
